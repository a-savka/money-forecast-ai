## 1. Цель MVP

Показать на защите работающий сценарий из питча («Путь клиента», шаги 2–3):

> Пользователь загружает выписку (или подключает «банк») → меньше чем за 2 минуты видит первый прогноз:
> **«До конца месяца вы потратите ≈ 45 000 ₽. Риск уйти в минус — средний»** + понятные рекомендации.

И дополнительно — **проверить продуктовую гипотезу о ценности ИИ-прогноза**: сравнить несколько подходов к прогнозированию по метрикам точности и показать результаты (это закрывает метрику «точность прогноза» со слайда «Что дальше» и вопрос «почему ИИ-прогноз точнее обычной аналитики» из рекомендаций к питчу).

### Что должно быть «по-настоящему»
1. Учёт операций (ручной ввод, импорт CSV, мок банка, QR чека).
2. Автокатегоризация операций.
3. Дашборд: структура трат, динамика, сравнение месяцев.
4. Прогноз расходов и баланса до конца периода, оценка риска кассового разрыва.
5. Рекомендации (где сократить, сколько можно отложить).
6. Несколько стратегий прогноза + бэктест + экран сравнения.

### Что делается моками
Авторизация, семейный режим, подписка/paywall/оплата, push-уведомления, лимиты по категориям, реальные банковские API, распознавание скриншотов (до подключения реальной LLM), партнёрские офферы, B2B API.

### Вне scope MVP
Реальные платежи, Open Banking, SMS-парсинг, мультивалютность, синхронизация офлайн-изменений, публикация в сторах.

## 5. Прогнозный движок (центральная часть MVP)

### 5.1. Что прогнозируем

`ForecastResult` (одинаковый для всех стратегий):

```json
{
  "strategy": "statistical",
  "as_of": "2026-11-12",
  "period_end": "2026-11-30",
  "current_balance": 38200,
  "expected_expense": 45000,          // до конца периода
  "expected_expense_p10": 39000,
  "expected_expense_p90": 52000,
  "expected_income": 60000,
  "by_category": [{"category": "Продукты", "expected": 12000, "spent": 7400, "limit": 15000}],
  "daily_balance": [{"date": "2026-11-13", "expected": 36500, "p10": 35000, "p90": 37800}],
  "upcoming_recurring": [{"name": "Аренда", "date": "2026-11-25", "amount": 30000}],
  "cash_gap": {"risk": "medium", "probability": 0.35, "first_negative_date": "2026-11-27", "min_balance": -2400},
  "safe_to_spend_per_day": 1150,
  "explanation": "..."                // текст (шаблон или LLM)
}
```

Горизонт: `week` (Free) / `month` (Premium) — ограничение через мок подписки.

### 5.2. Общий интерфейс

```python
class ForecastStrategy(Protocol):
    name: str
    def fit_predict(self, history: TransactionsFrame, as_of: date,
                    horizon_end: date, context: UserContext) -> ForecastResult: ...
```

Общие шаги для всех стратегий (`features.py`):
1. Перевод операций в дневные ряды по категориям (расходы/доходы).
2. **Детекция регулярных платежей**: группировка по мерчанту/описанию + близкая сумма + периодичность ~7/14/30 дней → `RecurringPayment` (аренда, подписки, связь, кредит, зарплата).
3. Разделение расходов на **регулярные** (известные даты и суммы) и **переменные** (прогнозируются моделью).
4. Прогноз баланса = текущий баланс + ожидаемые доходы − регулярные − переменные.

### 5.3. Гипотезы для сравнения

| ID | Стратегия | Как работает | Что проверяем |
|---|---|---|---|
| **H0** | `baseline` | Средний дневной расход за последние 30 дней × оставшиеся дни. Без регулярных платежей | Нижняя планка: «обычная аналитика», которую дают конкуренты |
| **H1** | `statistical` | Регулярные платежи по расписанию + переменные траты: экспоненциально взвешенное среднее по дням недели и по категориям, учёт «дня зарплаты» (траты после поступления дохода выше). Интервал P10/P90 — по эмпирическому распределению дневных трат (бутстрэп) | Насколько «умная статистика» лучше наивного подхода |
| **H2** | `stat_llm` | H1 считает числа → в LLM уходит **агрегированная** сводка (по категориям, неделям, регулярные платежи, прогноз H1, контекст: праздники, конец месяца). LLM возвращает структурированный JSON: поправочные коэффициенты по категориям с обоснованием + текст объяснения + рекомендации. Поправки ограничены (например ±30%), чтобы LLM не «галлюцинировала» числа | Добавляет ли LLM точности, или только ценность объяснений |
| **H3** | `ml_gbm` | LightGBM-регрессия дневных переменных трат. Признаки: день недели, день месяца, дни до/после зарплаты, лаги 1/7/14/28, скользящие средние, категория, праздник/выходной. Модель **глобальная** — обучается на всех синтетических профилях + истории пользователя; регулярные платежи — как в H1. Интервал — квантильная регрессия (objective=quantile) | Даёт ли ML выигрыш при малом объёме данных одного пользователя |
| H3b *(опц.)* | `ets` | `statsforecast` AutoETS по дневному ряду | Классический метод временных рядов как ещё одна точка сравнения |

> Важно для защиты: с точки зрения продукта «ИИ-прогноз» = вся связка (детекция паттернов + модель + LLM-объяснения). Сравнение покажет, какая комбинация реально точнее, — это честный ответ на вопрос комиссии «почему ИИ-прогноз точнее обычной аналитики».

### 5.4. Риск кассового разрыва и safe-to-spend (`risk.py`)
- Monte Carlo (≈500 сценариев): переменные траты сэмплируются из распределения стратегии, регулярные — по расписанию → доля сценариев с балансом < 0 = вероятность разрыва.
- Уровень риска: `low` < 15% ≤ `medium` < 40% ≤ `high` (пороги в конфиге).
- `first_negative_date` — медианная дата ухода в минус.
- `safe_to_spend_per_day` = (баланс + ожидаемые доходы − регулярные платежи − подушка) / оставшиеся дни.

### 5.5. Рекомендации (`recommendations.py`)
Два источника, одинаковый формат:
- **Правила** (работают всегда, в т.ч. с `MockProvider`):
  - категория растёт быстрее, чем в прошлом месяце → «сократить на X ₽»;
  - при риске разрыва — какие категории урезать, чтобы выйти в ноль (жадно по «дискреционным»: доставка, кафе, развлечения, маркетплейсы);
  - «можно отложить X ₽» при прогнозируемом профиците;
  - найденные подписки → «проверьте, нужны ли».
- **LLM** (H2): переформулирует и приоритизирует рекомендации человеческим языком, пример из питча: «Через 8 дней у вас закончатся деньги на категорию "Продукты". Рекомендуем сократить траты на доставку еды на 3 000 рублей».

### 5.6. Бэктест и метрики (`backtest.py`)
**Протокол (rolling origin):** для каждого профиля и для набора точек отсечения (например, 1, 10 и 20 число каждого месяца за последние 6 месяцев) стратегия видит только данные до отсечения и прогнозирует до конца месяца; результат сравнивается с фактом.

**Метрики:**
| Метрика | Что показывает |
|---|---|
| MAE, ₽ | Ошибка прогноза суммы трат до конца месяца |
| WAPE / MAPE, % | Относительная ошибка (WAPE устойчивее к малым суммам) |
| Ошибка по категориям | Где модель ошибается |
| Покрытие интервала P10–P90 | Калибровка неопределённости (цель ≈ 80%) |
| Precision / Recall кассового разрыва | Насколько верно предупреждаем об уходе в минус |
| Время ответа, мс; стоимость LLM-вызова | Практичность для продакшена |
| Качество рекомендаций (1–5) | Слепая оценка командой/респондентами H1-шаблонов vs H2-LLM |

**Датасеты:**
1. Синтетические профили (см. раздел 8) с разными «характерами»: стабильный, фрилансер с нерегулярным доходом, семья с крупными регулярными платежами, «импульсивный».
2. Реальные выписки членов команды (по согласию, анонимизированные) — 2–4 штуки за 6+ месяцев. Это самое ценное для честного сравнения.

**Выход:** таблица + графики на экране «Эксперименты» и Markdown/CSV-отчёт (`scripts/run_backtest.py`) для слайда защиты.

## 6. LLM-слой

```python
class LLMProvider(Protocol):
    name: str
    def complete_json(self, system: str, user: str, schema: type[BaseModel]) -> BaseModel: ...
    def vision_extract(self, image: bytes, schema: type[BaseModel]) -> BaseModel: ...  # опционально
```

- Адаптеры: `GigaChatProvider` (OAuth-токен по ключу авторизации, REST API Сбера), `YandexGPTProvider` (Yandex Cloud Foundation Models, API-ключ + folder_id), `MockProvider` (детерминированные ответы из фикстур — по умолчанию для разработки и тестов).
- Выбор провайдера: `LLM_PROVIDER=mock|gigachat|yandexgpt` в `.env`; на экране «Эксперименты» можно запустить H2 с каждым провайдером → сравнение провайдеров встроено в сравнение гипотез.
- Структурированный вывод: просим JSON по Pydantic-схеме, валидация, 1 повтор с сообщением об ошибке, при неудаче — fallback на H1 + шаблонные рекомендации (приложение никогда не «падает» из-за LLM).
- **Приватность (тезис для защиты, 152-ФЗ):** в LLM уходят только агрегаты (суммы по категориям/неделям), без описаний операций, номеров карт и ФИО. Российский провайдер — данные не покидают РФ.
- Кэширование ответа по хэшу входа; логирование токенов/стоимости в `BacktestRun`.
- Промпты хранятся файлами в `llm/prompts/` с версией — чтобы сравнения были воспроизводимыми.

> Перед подключением реальных провайдеров нужно получить ключи: GigaChat API (developers.sber.ru, есть бесплатный лимит для физлиц) и/или Yandex Cloud (грант для новых аккаунтов). Актуальные условия проверить при регистрации.

## 7. Импорт операций и категоризация

### 7.1. Источники
| Источник | Реализация | Статус |
|---|---|---|
| Ручной ввод | Форма «быстрого добавления»: сумма → категория (подсказка) → сохранить, ≤ 3 тапа | Реально |
| CSV/Excel | Загрузка файла → автоопределение кодировки (cp1251/utf-8) и разделителя → пресет банка или мастер сопоставления колонок (дата, сумма, описание, MCC, категория банка) → предпросмотр → подтверждение. Дедупликация по хэшу (дата+сумма+описание+счёт). Пресет: Т-Банк (CSV). Остальные банки — через универсальный мастер. **Формат колонок сверить на реальной выписке** | Реально |
| «Подключить банк» | Экран выбора банка → фейковая страница OAuth-согласия → «синхронизация» генерирует правдоподобные операции за 3–6 месяцев (генератор из раздела 8). Реализует историю «мультибанкинга» | Мок |
| Фото чека (QR ФНС) | QR кассового чека содержит строку вида `t=20261112T1830&s=1250.00&fn=…&i=…&fp=…&n=1` → дата и сумма парсятся **локально, без внешних API**. Сканирование: загрузка фото (web, zxing) или камера (Capacitor). Категория — по умолчанию «Продукты»/выбор пользователя. Получение позиций чека из ФНС — вне scope | Реально (только сумма/дата) |
| Скриншот из банковского приложения | `LLMProvider.vision_extract` → {сумма, дата, мерчант}; черновик операции на подтверждение. До подключения реальной LLM — `MockProvider` возвращает фиксированный результат | Мок → реально при наличии vision-модели |

### 7.2. Категоризация (каскад)
1. Пользовательские правила (`CategoryRule`, созданные после ручной правки).
2. Категория банка из выписки (маппинг «Супермаркеты» → «Продукты»).
3. MCC-код → категория (таблица ~100 популярных MCC).
4. Словарь ключевых слов мерчантов (ПЯТЁРОЧКА, ЯНДЕКС.ЕДА, WILDBERRIES …).
5. *(опц.)* LLM батчем для оставшихся «Прочее».
Метрика: доля операций, категоризированных автоматически (цель > 85% на синтетике).

## 8. Синтетические данные (`seed/synthetic.py`)

Нужны с первого дня: и для демо, и для бэктеста, и для обучения H3.

- 4 профиля по ЦА из питча: **«Молодой специалист»**, **«Семья»**, **«Фрилансер»** (нерегулярные поступления), **«Бросивший учёт»** (импульсивные траты).
- 12 месяцев истории; генерация: зарплата/аванс (или случайные поступления), регулярные платежи (аренда, ЖКХ, связь, подписки, кредит), переменные траты по категориям с эффектом дня недели, «после зарплаты», сезонность (декабрь, отпуск), шум и редкие крупные покупки.
- Детерминированность через `seed`; параметр «нагрузить конец месяца», чтобы в демо был **средний риск** кассового разрыва.
- Также генерирует до 50 «случайных пользователей» для обучения глобальной ML-модели.

## 9. Клиент: экраны и сценарии

Нижняя навигация: **Главная · Операции · Прогноз · Аналитика · Ещё**.

| Экран | Содержимое | Статус |
|---|---|---|
| Вход | Выбор демо-профиля / «Войти» (мок) | Мок |

| Главная | Карточка прогноза: «До конца месяца ≈ 45 000 ₽», индикатор риска, safe-to-spend на день, 2–3 топ-рекомендации, ближайшие регулярные платежи | Реально |
| Операции | Список с группировкой по дням, поиск/фильтры, редактирование категории, FAB «+»: вручную / QR чека / скриншот / выписка | Реально |
| Импорт | Загрузка CSV → маппинг → предпросмотр → результат (импортировано/пропущено) | Реально |
| Подключить банк | Список банков → «OAuth» → прогресс синхронизации | Мок |
| Прогноз | График баланса до конца периода с коридором P10–P90, отметка возможного ухода в минус, прогноз по категориям, переключатель «неделя / месяц» (месяц — Premium) | Реально |
| Рекомендации | Список карточек с эффектом в ₽ | Реально |
| Аналитика | Пончик по категориям, динамика по месяцам, сравнение месяц к месяцу | Реально |
| Эксперименты (для защиты) | Выбор стратегий/датасета → запуск бэктеста → таблица метрик + график «прогноз vs факт» для каждой стратегии; переключатель активной стратегии прогноза | Реально |
| Premium / Paywall | Сравнение тарифов Free vs Premium (299–499 ₽), кнопка «7 дней бесплатно» → флаг premium | Мок |
| Семья | Создать семью, код-приглашение, список участников и ролей, «общий бюджет» (сумма по участникам из сида) | Мок |
| Лимиты | Лимит на категорию, прогресс-бары, прогноз «закончится через N дней» | Мок (хранение + простой расчёт) |
| Уведомления | Настройки + кнопка «тестовое уведомление»; на устройстве — Capacitor LocalNotifications о риске разрыва, в вебе — in-app toast | Мок |

### Ключевой демо-флоу (≤ 2 минут)
1. Вход → онбординг → «Подключить Т-Банк» (мок) или загрузка CSV.
2. Через 2–3 секунды — главная с прогнозом и риском «средний».
3. Открыть «Прогноз»: график баланса, дата возможного ухода в минус.
4. Рекомендации: «сократить доставку на 3 000 ₽» → риск становится «низкий» (пересчёт «что если» — nice-to-have).
5. Попытка открыть прогноз на месяц → paywall → «7 дней бесплатно».
6. Добавить трату через QR чека.
7. Экран «Эксперименты»: сравнение H0–H3, вывод о лучшей стратегии.

## 11. Тестирование и качество

- **Backend:** pytest — парсеры CSV (фикстуры-выписки), парсер QR, категоризатор, детектор регулярных платежей, каждая стратегия прогноза на синтетике (ошибка не выше порога, формат результата), бэктест, API-тесты основных эндпоинтов (TestClient), `MockProvider` для всех LLM-путей.

- **Линтеры:** ruff + mypy (backend), ESLint + Prettier + `tsc --noEmit` (frontend). Pre-commit хуки.
- **CI (опц.):** GitHub Actions — тесты и линт на каждый PR.
